# 文言と用語

画面に出る日本語（本文・ラベル・ボタン・Toast・読み上げ名）の正本。書く前に読み、語と文の形をここに揃える。語の意味の正本は [ドメインモデル](../domain/domain-model.md) の「用語」表。

1. 原則：どう書き、何を書かないか
2. 語彙：用語、週の呼び名、使わない語、「」で囲む語、未決の語
3. 型：部品ごとの文の形と、数・時間・日付・記号の表記
4. 検査

## 1. 原則

### 語り口

- 丁寧体（です・ます）で短く。感嘆符、絵文字、煽り（「今すぐ」「最強」）を使わない。
- 決めるのは使う人。Agent や製品が決めたように書かない（「Sprint 14 を確定」「多めの 4時間を使う」）。Agent は「Agent」と呼び、擬人化しない（[Agent UI](agent-ui.md)）。

### 書き方の決まり

オーナーの方針は「状態を言い直すだけの説明文を足さない。短い語・見出し・操作の有無で伝える。行き先のように情報が増える文は残してよい」（Issue #159・#163）。1〜9 は、2026-10-01 の画面の文言の評価を受けて決めた（Issue #204〜#209。例はその旧 → 新）。10 はそれ以前からの決まり。11 は、2026-10-02 の画面の文字の量の評価を受けて決めた（Issue #241）。段階名を文に入れるときの「」は、語彙の「「」で囲む語」。

1. **状態を言い直すだけの文を足さない。** 見出し・ラベル・行の印・操作の有無で伝える。
   - しない：「確定したときの計画と、それぞれの結果です。ここでは変えられません。」
   - する：「ここでは変えられません。」（Issue #208）
2. **項目ごとに補足を並べない。** 補足は、行き先・期限・数のように情報が増えるときだけ置く。領域ごとなど部品ごとにくり返す説明は置かない（自己判定の「選ばなくても進めます」、目標のない領域の「目標なしでも計画できます」を消した。Issue #208）。
   - しない：領域ごとに「この領域の目標は任意です。タスクだけでも計画できます。」
   - する：消す。残す補足の例は「9/28 (月) に記録します。」（行き先の日。Issue #206・#208）
3. **安心させる一文を足さない。** 「〜しなくても進めます」「任意です」「理由は要りません」「システムは判定しません」は、操作の有無と見出し・必須の印で伝わる。書くなら見出しの近くに 1 回だけにする。
   - しない：「システムは判定しません。選ばなくても次へ進めます。」
   - する：消す（Issue #208）
4. **見た目の変化を文で説明しない。** 押せばわかることは書かない。
   - しない：「Backlog の □ で選ぶと、行が黄色の地とチェックになり、この下に領域ごとに並びます。」
   - する：消す（Issue #208 で「Backlog でチェックしたタスクが、ここに領域ごとに並びます。」に縮め、Issue #241 で消した）
5. **起きないことを断らない。** その操作で起きないことは書かない。
   - しない：「予定外の出来事をメモします。今日のタスクは組み替えません。」
   - する：「予定外の出来事をメモします。」（Issue #208）
6. **段階や仕組みを説明しない。** 記録のされ方や内部の段階ではなく、使う人がすることを書く。確定・完了で変わることと残る値は、使う人に要る情報なので、確認の Dialog と欄の説明に書く。
   - しない：「時間単位（例：1.5）。記録は残り、あとから足せます」
   - する：「あとから追加もできます」（Issue #206。単位の「時間で入力（例：1.5）」は、時間と分の 2 欄にしたので消した。Issue #252）
7. **1 文に条件を詰めない。** 条件や例外が重なるなら文を分けるか、数と行き先を「：」「·」で並べる。操作できない理由と直す場所は落とさない。
   - しない：「取り消すと、その日は未処理になります（見送りなどの後に完了した日は、元の状態に戻ります）。」
   - する：「取り消すと、その日は完了・スキップする前の状態に戻ります。」（Issue #209）
8. **仕様の語・モデルの語を出さない。** ドメインモデルや社内資料の語は、ふだんの言葉に言い換える（下の「使わない語」）。モデル名（Retro、Estimate など）は画面に出さず、用語表の「画面の語」を使う。
   - しない：「繰り返しの回：完了 3 · 未処理 0」
   - する：「繰り返し：完了 3 · スキップ 1 · 未完了 0」（Issue #205。スキップを入れた 3 つの形は Issue #245）
9. **同じものは同じ語で呼ぶ。** 見出し・ラベル・本文・Toast・読み上げ名で同じ語にする。
   - しない：同じものを「改善策」「次に試す変更」「次の Sprint で 1 つだけ変えてみること」と呼ぶ
   - する：どこでも「次に試すこと」（Issue #207）
10. **評価しない。失敗を責めない。** 割合や点数で語らず、数値は比べて並べるだけにする（振り返りのまとめの「計画 17時間15分〜20時間15分」と「実績 17時間45分」を並べる。補足は「見積もりなし 1件」「入力済み 8件」の数だけ。Issue #253）。
    - しない：「失敗」「遅れ」
    - する：「持ち越し」、自己判定は「できなかった」
11. **全部の行に同じ印を付けない。例外だけに付ける。** どの行にも当たることを行ごとに並べると、例外が埋もれる。同じ事実も、1 つの画面では 1 か所で言う（計画の「確かめる」の見積もりなしは、「見積もる」のある「見積もりなし」の節だけ）。
    - しない：各行に「目標に入っている」
    - する：目標に入っていない行にだけ「目標に入っていない」（Issue #241）

## 2. 語彙

モデル名（Retro、Estimate、SprintGoal など）とコードの識別子は英語のまま使い、画面には下の「画面の語」を出す（Issue #104）。Task は画面では「タスク」と書く（コードとモデル名は Task のまま。Issue #207）。「Task Row」のような部品の名前は、この文書の外の英語のまま。Sprint と Backlog は、ナビと製品の骨組みの名前として英語のまま残す（Issue #104 のオーナー決定。Issue #162 でも変えない）。Planning は画面では「計画」と書く（PR #116 のオーナー決定）。

### 用語

| 画面の語 | モデル | 意味と表記 |
| --- | --- | --- |
| Sprint | Sprint | 1 週間の計画単位。「Sprint 14」。カタカナにしない |
| Backlog | Backlog（ビュー） | active なタスクの一覧。Sprint や Today に入っても消えない。今の Sprint に入っているタスクには「今週」、来週の計画にも入っていれば「今週 · 来週」（来週だけなら「来週」） |
| 計画 | Planning（Sprint = planning） | 次の Sprint の計画を立てること。ボタン「Sprint 14 の計画を始める」と Status「計画中 · 未確定」に使う。文の中の「計画」は値（「計画 5時間」）と行為（「このルールで計画する」）に絞り、段階は「次の Sprint」と書く（「次の Sprint では、このルールは出ません。」「次の Sprint には何も出ません」「次の Sprint を計画するときに表示されます。」。Issue #245）。画面に「Planning」と書かない |
| 領域 | Area | 仕事・研究など、本人が作る領域。画面では各 Area の名前を出し、「カテゴリ」と呼ばない。未設定は「領域なし」 |
| 目標 | SprintGoal | Sprint × 領域の「今週の終わりにどんな状態にしたいか」。「〜な状態にする」「〜を終える」。任意。見出しは「今週の目標」、入力は「目標を書く」 |
| 目標に入っている / 入っていない | SprintTask.goalLink | 行の状態。操作は「目標に入れる / 目標から外す」。「目標なし」と略さない（目標のない領域と読み違えるため。Issue #159）。「紐づく」「紐づける」と書かない（Issue #205）。行には、目標のある領域で目標に入っていないタスクにだけ「目標に入っていない」と出し（アイコンなし、ほかのメタデータと同じ調子）、入っているタスクには何も出さない（原則の 11。Issue #241。それまでは両方を出していた、Issue #159）。目標に入っていないタスクも時間に含める。確かめるの件数は「（うち目標に入っていない 1件）」。振り返りの表の見出しは「目標に入っているタスク / 目標に入っていなかったタスク」 |
| 見積もり | Estimate | 本人が確定した点の値。「3時間」「30分」。入力欄のラベルは「見積もり」で、「時間」「分」の 2 欄に入れる（単位の説明は書かない。Issue #206・#252） |
| 見積もりの提案 | EstimateSuggestion | 製品が出す幅。「見積もりの提案 2〜4時間」（破線）。何の提案かを語で示す。ただし行（Backlog の一覧、計画の選ぶの左の Backlog）の破線の札は、見積もりの位置にあるので「提案 2〜4時間」と縮める（読み上げは「見積もりの提案（未確定）：2〜4時間」のまま）。計画の今週のタスクの行（選ぶの右、整える、確かめる）では札を出さず、計画の時間の後ろに「（提案）」、計画のルールが効く行は「（提案の多めの値）」と添える。繰り返しのタスクは 1 回あたりの提案に回数を掛けた値なので「4〜8時間（提案 × 4回）」「8時間（提案の多めの値 × 4回）」（Issue #250 のオーナー決定）。出所は「Itera · 10/1 (木) 14:02」（「製品内の見積もり支援」と書かない。Issue #206）。幅の 3 つの値は「少なめ / ふつう / 多め」（「2〜4時間 ふつう 3時間」、ボタンの読み上げ名「多めの 4時間を使う」）。「少なく済めば / 多くかかれば」と同じ「少ない・多い」の軸にそろえ、「下限 / 中央 / 上限」と書かない（Issue #234）。Task の詳細では、提案の幅をカードで 1 回だけ言い（見出しが「見積もりの提案」なので、値の末尾に「提案」を付けない）、「計画の時間」の選択肢には出さない。振り返りの表の見積もりの列は、提案の幅だけを出す（見積もりは点の値なので、幅は提案と読める。compact の縦積みは「見積もりの提案 3〜5時間」のまま。Issue #241） |
| 使う / 直して使う / 使わない | Estimate.source ほか（モデルの採用・編集して採用・却下） | 見積もりの提案を本人の値にすること（採用）。提案の少なめ・ふつう・多めのどれかを選ぶ（「多めの 4時間を使う」、source に記録）。画面では「使う：」の後に値だけのボタンを 1 行に並べ（「使う：［2時間｜3時間｜4時間］」）、「多めの 4時間を使う」は各ボタンの読み上げ名にする（Issue #242）。値を直してからは「直して使う」（欄のラベルは「使う見積もり」）、使わないときは「使わない」。結果の 1 行は「見積もりを 4時間にしました」「提案を使いませんでした」。画面に「採用」「却下」と書かない（Issue #206 のオーナー決定。モデル名とコードの識別子は採用のまま）。計画のルールには使わない（「適用」の行。Issue #224 で振り返りを完了できない理由の文に許した例外は、Issue #245 でなくした） |
| 確定したとき | Sprint = Active への遷移の時点 | 確定の時点を指す語。「確定時」「計画時」「計画したとき」と書かない（「確定したときの計画」「確定したときとの差」「確定したとき 17時間 → 今 14時間」。Issue #207） |
| 計画の時間 | PlanningValue | 今回の計画に使う時間。値の前のラベルは「計画 5時間」。行（今日・計画・Sprint）では「計画」を付けず値だけにし、同じ行にほかの時間（「実績 2時間」「中断 · 1時間30分」）があるときだけ「計画 5時間」と書く（原則の 11。読み上げは「計画の時間 5時間」。Issue #250）。Task の詳細で見積もりとサブタスクの合計のどちらを使うかを選ぶ欄の見出しも「計画の時間」（「計画に使う時間」と書かない。Issue #206）。Sprint 確定時（追加分は追加時）に固定 |
| 計画のルール | PlanningCriterion | 前の振り返りで決めた、見積もりがないときに提案のどの値で計画するかのルール。名前の形は「{領域}：見積もりなしは提案の{少なめ / ふつう / 多め}の値で計画」（「研究：見積もりなしは提案の多めの値で計画」）。すべての領域は頭を付けて「すべての領域：見積もりなしは提案の少なめの値で計画」とし、形を 1 つにする（「領域なし」と取り違えない）。名前をコードで作るのは `lib/criterion-text.ts` の 1 か所だけで、選ぶ・整える・確かめる・Sprint の画面・事実を見る・引き継ぐ・完了の Dialog が同じ名前を使う。文の中に入れるときは名前全体を「」で囲み、コロンを重ねない（「今回の計画のルール「研究：見積もりなしは提案の多めの値で計画」」）。見出しや行に 1 つだけ置くときは囲まない。名前が条件（見積もりなし）と効果を言うので、ルールのカード（確かめるの枠、引き継ぐの新しいルールのプレビュー）の 1 文目は名前を言い直さず、件数と効果だけにする（Issue #254。計画のルールの Select の選択肢も「少なめの値 / ふつうの値 / 多めの値」と書く。それまでは「研究：提案の多めで計画」で、条件はカードで言っていた、Issue #241。「多め」で止める言い方がふつうの日本語にないため、「多め」は単独で使わず「多めの値」と書く。「多めに見て」は「大目に見る」に読めるので使わない） |
| 適用 | CriterionUse.appliedAtConfirm | 計画のルールで今回の計画の時間を決めること。Switch は「このルールで計画する」。見積もりは変わらない。画面に「適用」と書かず、見積もりの提案の「使う」とも混ぜない。ルールには「使う」と書かない（Issue #245 の決定）。確定の Dialog の値は「「研究：見積もりなしは提案の多めの値で計画」 · このルールで計画する」、オフなら「 · 今回はこのルールで計画しない」。効果と結果は「幅のあるタスク」と呼ばず、どう計画したかで言う（確かめるの枠は「対象は 1件です。少なく済んだときの合計が 2時間増えます。」、引き継ぐの結果は「提案の多めの値で計画した研究のタスク 2件のうち、1件を持ち越し（計画 5時間・実績 4時間30分）」）。条件の「見積もりなし」は名前が言うので、カードで言い直さない（Issue #254）。新しいルールのプレビューは名前の下に件数だけを言う「対象は 2件です（今の Backlog で）。」で、0 件のときは「対象は、今の Backlog にはまだありません。」（Issue #206・#254）。結果の文「提案の多めの値で計画した研究のタスク 2件のうち…」は、すべての領域のルールでは「研究の」を外す（Issue #206 のオーナー決定）。引き継ぐの「続ける」「置き換える」の説明は効果を言い直さず、どちらも「このルールで計画するかは「確かめる」で選べます。」（Issue #241）。「終える」は「次の Sprint では、このルールは出ません。」、完了の Dialog の新しいルールは「新しい計画のルール「…」を、次の Sprint から出す」（Issue #245）。合計の動きは「少なく済んだときの合計が 2時間増えます。」「多くかかったときの合計が 1時間減ります。」と書き、両端が変わるときは「少なく済んだときの合計が 1時間増え、多くかかったときの合計が 1時間減ります。」の 1 文にまとめる（Issue #234） |
| 使える時間 | Sprint.availableHours | 今週、計画に使える時間（本人が入力）。「使える時間 18時間」。入力欄は「時間」「分」の 2 欄で、単位の説明は書かない（実行中の Sprint では説明に「確定後も変えられます（確定したときの値は残ります）。」。Issue #206・#252）。確定後は「確定したときの使える時間」と、変えられる「使える時間」 |
| 計画の合計 | — | 計画の時間の合計（幅のまま）。「計画の合計 16時間30分〜18時間30分」 |
| 少なく済めば / 多くかかれば | — | 使える時間と計画の合計の差。合計の両端を、同じ型の 2 つの文で言う（Issue #162・#234）。収まる：「少なく済めば 3時間残る · 多くかかっても 1時間残る」。0 をまたぐ：「少なく済めば 2時間15分残る · 多くかかれば 45分超える」。超える：「少なく済んでも 3時間超える · 多くかかれば 5時間超える」（数字は `danger`）。端の差が 0 なら「ちょうど収まる」（「少なく済めばちょうど収まる」「多くかかってもちょうど収まる」）。合計に幅がないときは 1 文（「3時間残る」「ちょうど収まる」「1時間超える」）。状態の文は「使える時間の範囲に収まっています。」「超える可能性」「超える」で、数字を繰り返さない。確かめるの要約は、状態の文の下に 2 つの文を 1 行ずつ置く（Issue #243）。振り返りの事実を見るでは、まとめの直下に使える時間を頭にした 1 行で出す（「使える時間 17時間：少なく済んでも 15分超える · 多くかかれば 3時間15分超える」。確定したときに未入力なら「使える時間は未入力」。確定の後に使える時間を変えた週は「確定したときの使える時間 17時間：…」「確定したときの使える時間は未入力」。計画の合計がない週は出さない。Issue #253）。見出しのない場所（確定の Dialog）の行は「超える可能性：少なく済めば 2時間15分残る · 多くかかれば 45分超える」、超えるときは「超える：」を付けずアイコンと 2 つの文だけにする。「残り 1〜3時間」「超過 3〜5時間」の範囲にしない |
| 優先度 | Task.priority | 「高 / 通常 / 低」（「普通」と書かない）。行の Task Metadata には高と低だけ「優先度 高」「優先度 低」と出し、通常は出さない。並び・絞り込みには使わない（不変条件 5。Issue #97） |

### 週の呼び名

Issue #90 で定めた（オーナーの確認は PR で取る）。画面の組み立ては [画面のパターン](patterns.md) の「どの Sprint も開く」。

- 実行中の Sprint があるあいだは、それを「今週」、その次の Sprint を「来週」と呼ぶ。
- 実行中の Sprint がない（前の Sprint が振り返り中か完了）ときは、次に始まる Sprint を「今週」と呼ぶ。
- 「今週」の前の週の Sprint は「先週」と呼ぶ（Issue #168。オーナーの確認は PR で取る）。Sprint Header で期間の前に添えるだけで、見出し・案内文・Toast は「Sprint N」のままにする（「Sprint 2 で何が起きたか」）。週が空いて前の週に Sprint がなければ、「先週」はない。
- どれにも当たらない Sprint は「Sprint N」と呼ぶ（それより前の Sprint）。
- 見出し・案内文・Toast・読み上げ・行とグループの語の「今週」は、開いている Sprint の呼び名に置き換える（「来週、何を進めるか」「来週の繰り返し」「来週から外す」「来週 3回」）。「Sprint N」のときは、欧文の後に半角スペースを入れる（「Sprint 2 で何が起きたか」「Sprint 1 の計画と結果」）。
- 「今週」「来週」は画面を分ける単位ではなく、どの Sprint も同じ画面で開ける中の呼び名。例文（「今週、何を進めるか」「3件を今週に入れました」）は、ふだんの場合の例として書く。

### 「」で囲む語

- **見積もり以外の Agent 提案のボタンの語。** 見積もりの提案だけ「使う / 直して使う / 使わない」に決めた（Issue #206）。DESIGN.md の振り返りの材料の「振り返りに加える / 編集して加える / 却下」と、計画案の差分の「すべて却下」はまだ画面がなく、決めていない。
- **振り返りの材料の種類の名前。** DESIGN.md の振り返りの材料（RetroInsight）は、種類を「事実」と書いている。画面の本文では「事実」を「記録」と書く（Issue #205）が、種類の名前を画面に出すときの語は決めていない。

## 3. 型

部品ごとの文の形。語は「2. 語彙」、書かないことは「1. 原則」に従う。

### 文の長さ

- 1 文は 40 字までを目安にする（差し込む値は、タスク名や日付の分として 4 字と数える）。超えるときは、原則の 7 のとおり文を分けるか、数と行き先を「：」「·」で並べる。`pnpm copy:lint` の `long-sentence` がこの字数を読む。
- 1 つの文言に「〜ます。」を続けない。3 つ続いたら、消せる文がないか（原則の 1〜6）を見る（`many-masu`）。

### ボタン

- 動詞で終える（「Sprint 14 を確定」「追加」「保存」「差分を確認」「元に戻す」）。対象があれば前に置く（「かかった時間を記録」「割り込みを編集」）。見積もりの提案は値を入れる（読み上げ名は「多めの 4時間を使う」。見えるのは「使う：」の後の値だけ。Issue #242）。
- 「直す」と書かず、「編集」に揃える（「割り込みを編集」）。「そのほか」ではなく「その他」（グループ名も「その他の操作」も）（Issue #207）。
- 段階を進めるボタンは「次へ：」に段階名を続ける（「次へ：振り返る」「次へ：引き継ぐ」）。段階表示の名前と揃え、押した後に開く段階を書く。「〜へ」で終えない（Issue #168）。
- 「OK」「はい / いいえ」を使わない。確認 Dialog のボタンは下の「確認の Dialog」。

### Toast

- 結果を「〜しました」の 1 文で言い切る（「3件を今週に入れました」「Sprint 14 を確定しました」「見積もりを 4時間にしました」「提案を使いませんでした」）。次にできることは操作で添える（「元に戻す」「今日を開く」）。
- 名前は「」で囲む（「「{タスク名}」を「今日やる」に入れました」）。
- 「今週」は開いている Sprint の呼び名に従う（「週の呼び名」。実行中の Sprint があるあいだの次の計画では「3件を来週に入れました」）。
- 表示の時間・位置・積み方は DESIGN.md の Toast。

### 読み込み中

- 読み込みが 300ms 続いたら、Progress（indeterminate）のラベルに読んでいるものを名詞で書き、数値の位置に「読み込み中…」を出す（DESIGN.md の Progress と Loading）。ラベルは「タスクの一覧」「この日の記録」「この Sprint の記録」「Sprint の一覧」「パスキーの一覧」「領域」「計画」。
- すぐ上の見出しと同じ語にしない（見出し「振り返り」の下は「この Sprint の記録」、見出し「パスキー」の下は「パスキーの一覧」。原則の 1。Issue #276・#312）。

### 読み込みの失敗

- danger の Notice にする。見出しは「読み込めませんでした」、操作はボタンの「もう一度読み込む」。説明の文は置かない（Issue #273）。
- 何を読めなかったかは、画面や節の見出しが言う。見出しが言わない場所でだけ、Notice の見出しに対象を入れる（最初の設定の「サインインの情報を読み込めませんでした」。Issue #279）。

### 送信中のボタン

- 送信が 300ms 続いたら、ボタンのラベルを「〜中…」にする（スピナー・幅・押せなさは DESIGN.md の Button の Loading）。形はこの 1 つにし、「〜しています…」と書かない（Issue #312）。
- 語は、ボタンの動詞から対象を除いたもの（「追加」→「追加中…」、「Sprint 14 を確定」→「確定中…」、「パスキーを追加」→「追加中…」、「保存」→「保存中…」、「サインアウト」→「サインアウト中…」）。
- 「中」を付けると読めない動詞と、入力を送る「記録する」は、押した後に起きていることの「保存中…」にする（「振り返りを完了」「今日は中断する」「記録する」、設定を保存する最初の設定の「始める」）。「完了中…」と書かない。「記録中…」は記録を取っている最中に読めるので使わない。
- 入力を送らずに段階を始めるボタンは「開始中…」にする（「Sprint 14 の計画を始める」「振り返りを始める」）。何も入力していないので「保存中…」とは言わず、「始めています…」とも書かない。タスクの「開始」と同じ語だが、送信中の一瞬だけ「〜を始める」のボタンの上に出るので取り違えない（Issue #312。司令塔の判断で、オーナーの確認を待つ）。
- 押した後に、ほかの画面や端末の操作を待つものは、待っていることを書く（「パスキーでサインイン」→「パスキーを確認中…」、「Google でサインイン」→「Google に移動中…」。Issue #278）。

### 保存の失敗

- 記録を変える操作が通らなかったときは、danger の Toast を出す。見出しは操作によらず「保存できませんでした」、説明は記録の状態と次にすることの 2 文「記録は変わっていません。内容を確かめてもう一度試してください。」（Issue #272 のオーナー決定）。
- タスクや Sprint の記録を変えない操作（サインイン、サインアウト、パスキーの追加）が通らなかったときは、見出しを「{ボタンの語}できませんでした」にし、説明に次にすることを 1 文で書く（「サインアウトできませんでした」「もう一度試してください。」、「パスキーでサインインできませんでした」「別のパスキーか、Google でサインインしてください。」）。Toast か Notice かは場面による（DESIGN.md の Toast と Notice）。
- 通らなかった理由が分かり、その理由で次にすることが変わるときは、見出しで理由を言う（「この Google アカウントでは使えません」と説明「別の Google アカウントでサインインしてください。」、「もう一度サインインすると追加できます」と操作「もう一度サインイン」、「このパスキーは追加済みです」）。使う人が直せない理由は danger、手順で済むことと、すでに済んでいることは info にする（Issue #278・#312）。
- 「エラー」「失敗しました」と書かない。何ができなかったかを書く（原則の 10）。
- 保存できたかが分からない失敗は、見出しを「保存できたかわかりませんでした」、説明を記録の状態と次にすることの 2 文「記録が変わったかもしれません。最新の記録を見てください。」にする（上の型と同じ。「記録は変わっていません」とは言わない。この Toast の見出しと説明で同じ語を重ねない。Issue #313）。

### 見出し

- 名詞で終える（「次に試すこと」「今週の繰り返し」「まとめ」）。空の状態と、見つからないときの見出しは文にしてよい（「来週の計画はまだありません」「ページが見つかりません」）。段階の問いの見出しは「〜か」で終え、「〜ますか」にしない（「今週、何を進めるか」「Sprint 2 で何が起きたか」。Issue #207）。
- すぐ下の文で見出しを言い直さない（原則の 1）。

### 空の状態

- ないことを 1 文で言う（「まだありません。」「該当するタスクはありません。」「進行中の Sprint はありません。」）。
- 続けるなら、どこで何をすれば入るかを 1 文だけ書く（「まだありません。下の「今週の残り」から「今日へ」で入れられます。」「「振り返りに使う」を付けた記録が、ここに集まります。」）。「〜しなくても進めます」を添えない（原則の 3）。
- 目標のない領域は「+ 目標を書く」だけにし、案内の文を置かない（DESIGN.md の Goal の empty。Issue #155・#208）。

### 補足

- 見出しや欄の下に置く小さな文。行き先・期限・数のように情報が増えるときだけ、1〜2 文で書く（原則の 2）。行き先は「9/28 (月) に記録します。」「次の Sprint を計画するときに表示されます。」の形。
- 完了した振り返りは、変えられないことだけを 1 行で書く（「完了した後は、書いた内容を変えられません。」）。直せる場所がないので、行き先は書かない。完了の確認 Dialog の説明も、同じことを先に伝える（「完了すると、書いた内容は変えられず、この Sprint にはかかった時間を記録できなくなります。」。Issue #168）。

### 入力欄のラベルと placeholder

- ラベルは名詞（「見積もり」「かかった時間」「使える時間」）。
- 時間の入力は、画面の書き方（「1時間30分」）と同じ「時間」と「分」の 2 欄にする（見積もり・かかった時間・使える時間・サブタスクの見積もり・割り込み）。2 欄をラベルの名前のグループにし、各欄の読み上げ名は「時間」「分」。単位は欄が示すので、ラベルにも説明にも書かない（「（h）」「（時間）」「時間で入力」と書かない）。見出しを隠す行のグループ名は「見積もり：{タスク名}」（Issue #206・#252）。
- placeholder に例を出すときは「例：」で始める（「例：障害対応、急な来客」「例：論文は 1本ずつタスクに分ける」）。ラベルの代わりにしない（[アクセシビリティ](accessibility.md)）。
- 入力のエラーは、何を入れればよいかを書く（「1分以上の時間を数字で入れてください」。Issue #252）。

### 確認の Dialog

- ボタンは結果を書く（「戻って調整」「Sprint 14 を確定」）。
- 日ごとの記録の取り消しのように、やめても何も起きない確認は、やめるボタンを「キャンセル」、確認するボタンを何をするかで書く（「完了を取り消す」「スキップを取り消す」）。「やめる」「取り消す」だけにしない。やめた先に別の行き先がある確認（計画の確定の「戻って調整」、振り返りの完了の「戻る」）は、行き先を書く（Issue #207）。
- 説明は、確定・完了で変わることを先に 1〜2 文で書く（「確定すると、各タスクの計画の時間は変わらなくなります。目標と使える時間はあとからでも変えられます。」。Issue #209）。
- 見出しが日付とタスク名を言うときは、説明で重ねない（「その日の記録と繰り返しは未完了に戻ります。」。Issue #205）。

### 操作できない理由

ボタンを無効にするときは、近くに「何をすれば押せるか」を書く。責める言い方や「エラー」を使わない。

| 場面 | 文言 |
| --- | --- |
| Planning の確定（前の振り返りが未完了） | 前の Sprint の振り返りを完了すると確定できます。前の Sprint が実行中なら「Sprint 2 の振り返りは 10/4 (日) から始められます。」を続ける（F21、Issue #90）。 |
| Planning の確定（完了・アーカイブしたタスクが残っている） | 完了・アーカイブしたタスクを今週から外すと確定できます。（「今週」は週の呼び名に従う） |
| 次の週（計画を始める前。Issue #90） | 確定できるのは、前の Sprint（Sprint 2）の振り返りを完了してからです。Sprint 2 の振り返りは、最終日の 10/4 (日) から始められます。（振り返り中なら「Sprint 2 は振り返り中です。」と振り返りへのリンク） |
| Backlog の今日へ（Sprint の開始日より前。Issue #59） | Sprint 2 が始まる 9/28 (月) から選べます。（行のメニューでは「今日へ · 9/28 (月) から」） |
| 振り返りの完了（計画のルールの決定がまだ。不変条件 36。Issue #106） | 上の「今回の計画のルール」で、続ける・終える・置き換えるのどれかを選ぶと完了できます。 |
| 振り返りの完了（「続ける」のまま新しい基準の下書きがある。不変条件 35。Issue #106） | 新しいルールにするなら、「今回の計画のルール」で「置き換える」を選んでください。今回のルールを続けるなら、「計画のルールにもする」をオフにしてください。（Issue #245。オーナーが決めた文は「今のルールを続けるなら」で、使わない語の「今のルール」（→ 今の設定）に当たるので、司令塔の判断で見出しと同じ「今回のルール」にした。Issue #224 の「使うなら」を、ルールに「使う」と書かない形にした） |

次に試すことが空でも振り返りは完了できる（Issue #42 のオーナー決定）。押せるときだけ、完了ボタンの下に「次に試すことがないまま完了します。次の Sprint には何も出ません。」と中立に添える。押せないときは、押せない理由だけを出す（Issue #106）。

### 読み上げ名

- 画面の語と同じ語にする（原則の 9）。見えない名前だけ別の語にしない。例外：見積もりの提案の値のボタンは見えるのが値だけ（「使う：」の群の「4時間」）なので、読み上げ名に少なめ・ふつう・多めの語と「を使う」を足す（「多めの 4時間を使う」。見える値を名前に含める。Issue #242）。
- 操作は「操作：対象」の形にする（「今週に入れる：{タスク名}」「かかった時間を記録：{タスク名}」「その他の操作：{タスク名}」）。対象の付け方と、Drawer・行の `…` の名前は [アクセシビリティ](accessibility.md)。
- 行の印も語にする（「1回ずつ完了」）。時間の読み方は下の「日付と時刻」。

### 数・時間・日付・記号の表記

- 送り仮名は「見積もり」に揃える。
- 表記は「Sprint 14」。欧文を大文字だけで組んだ飾りのラベル（「SPRINT 14」）は使わない。
- 和文と欧文の間は半角スペース（「Sprint 14 を確定」）。数字と助数詞・単位は詰め、単位の後ろの和文も詰める（「3件」「2日」「1時間30分」「3時間残る」「多めの 4時間を使う」）。時間は「時間・分」で書き、小数の「h」「m」を出さない（1 時間未満は「30分」、ちょうどなら「3時間」、0 は「0時間」。Issue #239）。範囲は空白なしの「〜」（「2〜4時間」「30〜45分」「1時間30分〜3時間」「9/28〜10/4」「9/28 (月)〜10/4 (日)」）。両端の単位が同じなら前の単位を省き、違えば両端に付ける（下の端の 0 も同じ扱いで「0〜30分」「0〜2時間」「0時間〜1時間30分」）。負の値は画面に出さないが、出すなら負号「−」（U+2212）を付け、範囲では両端に単位を付ける（「−1時間〜1時間」）。使える時間との差は範囲にせず、合計の両端の 2 つの文にする（「少なく済めば 3時間残る · 多くかかっても 1時間残る」。語彙の「少なく済めば / 多くかかれば」。Issue #93、#162、#234）。
- コロンは全角「：」で、後ろに空白を入れない（「今の設定：毎週 土」「使える時間：」「例：1.5」。読み上げ名も同じ。「その他の操作：{タスク名}」）。曜日付きの日付や名前をかっこの中に入れて入れ子にしない（「前の日：9/30 (水)」。「前の日（9/30 (水)）」と書かない）。日付を添えるときは「·」か「の」でつなぐ（「毎週 土 · 10/4 (日) まで」「最終日の 10/4 (日) から」）。予定している変更は「変更：」を前に置く（「毎週 土 · 次は 10/3 (土) · 変更：10/5 (月) から 毎週 日」）（Issue #207）。
- 「」の内側と、和文と「」の間に空白を入れない（「「今日やる」に入れました」）。
- 数を並べるときは「：」と「·」でつなぎ、文にしない（「持ち越し 5件：次の Sprint に 2件 · Backlog に 3件」「繰り返し：完了 3 · スキップ 1 · 未完了 0」。Issue #205・#209）。

#### 日付と時刻

- 日付は「9/28 (月)」。見出しの日付は「9月29日（火）」（全角括弧）。範囲は「9/28 (月)〜10/4 (日)」。
- 相対は「あと2日」「今日まで」「2日過ぎ」。「明日」「昨日」は 24 時間以内の記録にだけ使う。
- 時刻は 24 時間表記（「14:02」）。「2分前」は 1 時間以内だけ、それ以降は時刻。
- 日付と時刻を並べるときは「9/30 (水) 14:02」。Retro の割り込みなど、いつの出来事かが要る記録に使う。
- 時間の読み上げは、画面の値と同じ文字列にする（「3時間」「30分」「2〜4時間」「1時間15分〜2時間」）。「1.25時間」と書かない（Issue #206・#239）。

## 4. 検査

書くとき・検査・レビュー・定期の評価の 4 か所で、この文書の決まりを確かめる（Issue #211・#213）。

| どこで | 何を | 使うもの |
| --- | --- | --- |
| 書くとき | この文書を読んで型に沿って書き、`pnpm copy:lint` と自己点検で確かめる。迷う語はオーナーに 2〜3 案で聞く | `ui-copy` Skill |
| 検査 | 画面の文言を抜き出し、下の規則で警告を出す。警告だけで、`pnpm check` を落とさない | `pnpm copy:lint` |
| レビュー | 画面の文言が変わる PR で、この文書との照合、警告の扱い、ふだんの言葉か、AI が書いたように読める型、語の揃い、読み上げ名、旧 → 新の表を見る | issue-harness の `copy` 観点 |
| 定期の評価 | 画面の文言の全件を、ペルソナを演じる評価役に読ませて集計する（評価役は実際の利用者ではない） | `pnpm copy:list` と `copy-review` Skill |

### pnpm copy:lint

`pnpm copy:list` と同じ抜き出し（`apps/web/src` と `packages/domain/src`。テスト・Storybook・fixture・開発用メニューを除く）に、次の規則を当てる。語の表はこの文書から読み、検査側に写さない。文字の並びのパターンだけを `tooling/copy/lint.mjs` に置く。

確実（直す）：

- `banned-word`：「使わない語」の表の語。例外の列の「」の句の中の出現は外す。
- `unquoted-term`：「「」で囲む語」の表の語が、「」なしで名詞として文に入っている（「整えるで」「今日やるに入れました」）。
- `colon` / `nested-parens` / `bracket-space` / `counter-space` / `middle-dot`：「数・時間・日付・記号の表記」のコロン、かっこの入れ子、「」の前後の空白、数字と助数詞の間の空白、数を並べる「・」（「時間・」「分・」も見る）。
- `time-format`：「数・時間・日付・記号の表記」の時間と範囲。小数や「h」「m」の時間（「1.5h」「30m」）、数字の間の en dash（「2–4h」「9/28 (月) – 10/4 (日)」）、前後に空白のある「〜」（「1 〜 3時間」）（Issue #239）。
- `term-table`：用語表の「画面の語」の列に、使わない語が入っている。
- `loading-label`：型の「送信中のボタン」。ボタンの `loadingLabel` が「〜中…」の 1 形でない（「始めています…」「保存中...」）。

目安（考える）：

- `long-sentence` / `many-masu`：型の「文の長さ」。
- `reassurance`：原則の 3 の安心させる型（「〜なくても〜できます」「〜しても大丈夫」「〜は変わりません」など）。

出力は 1 行 1 件（ファイル:行、規則、文言、語と使う語）で、最後に規則ごとの件数を出す。終了コードは常に 0。`pnpm copy:lint --strict` のときだけ、警告があれば 1 を返す（警告をエラーにするかはオーナーが決める）。
