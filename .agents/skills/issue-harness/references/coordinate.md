# 司令塔：複数の Issue を並列に進める

独立した Issue を同時に進めるとき、1 つのセッションが司令塔になり、Issue ごとに worker のセッションを動かす。一続きの並列実行を Run と呼ぶ。並列実行の道具（worktree の作成、worker の起動・監視・メッセージ）は問わない。道具に固有の操作は別に書く。Orca を使うときは [Orca での操作](coordinate-orca.md)も読む。

## 役割

| 役割 | 担当 | やらないこと |
| --- | --- | --- |
| 司令塔 | 計画、起動、伝達、監視、マージ、統合の確認、報告 | 実装とレビュー（worker の worktree を編集しない） |
| worker | 1 つの Issue を SKILL.md の「Issue を実装する」の手順で、レビューと PR 作成まで | マージ、ほかの Issue の作業 |
| オーナー | 計画の了承、製品の判断、Run の停止と再開 | — |

- 1 Issue＝1 worker＝1 worktree。小さな Issue を 1 つの PR にまとめるときは計画に書く。
- worker の Reviewer は worker 自身が起動する。司令塔は Reviewer を起動しない。
- マージした後に続き（範囲内の小さな直し）があれば、同じ worker に新しい依頼として渡す。続きがないと確かめてから worker を解放する。解放した後に出た続きは、新しい worker に渡す。

## Run の計画

起動の前に計画を作り、オーナーの了承を得る。了承の前に worker を起動しない。計画に書くこと：

1. 対象の Issue と、それぞれの向き先のブランチ（`main` か統合ブランチか）。
2. 依存：どの PR がマージされたら、どの Issue を起動できるか。
3. 同時に動かす worker の数（既定は 3）と組み合わせ。触るファイルが重ならない組にする（API と画面のように別の領域どうし）。同じファイルを触る Issue は順に並べる。
4. Issue ごとのモデルと effort。既定は、ドメインや土台が Opus、画面が中心のものが Sonnet、effort は high。
5. オーナーに確認してからマージ・着手するもの（語の最終確認、規則の決定、画像での比較など）と、範囲外にするもの。
6. Issue ごとの実作業の上限。
7. 止める地点（どこまで進めたら止めるか）。
8. オーナーが不在になる時間があれば、その間の任せ方（既定は「止める・再開する」の「オーナーが不在の間」）。

既定の値はオーナーが Run ごとに変えられる。依存の前提が `main` 向けの PR なら、それを `main` にマージし、`main` を統合ブランチに取り込んでから後続を起動する（道具の依存の機能では、この順を表せないことがある）。取り込みは司令塔が PR で行い、CI の成功を確かめてからマージする。

## worker への依頼

依頼に書くこと：

- 担当の Issue、worktree の元のブランチ、PR の向き先。統合ブランチ向けの PR は `Closes` が効かないので `Refs` にする。
- 守る手順：AGENTS.md と SKILL.md の「Issue を実装する」に従い、レビューまで行う。マージはしない。担当外の Issue は編集しない。
- 使わないコマンド：パッケージを取得して実行するもの（`npx`・`npm`・`pnpm dlx`）は使わず、`pnpm exec`・`pnpm test`・`pnpm check` に読み替える。許可の確認で止まるため。
- 扱わない操作：秘密の値、デプロイ、本番の資源への操作。本番でしか確かめられないこと（デプロイ後の確認など）は、ローカルと CI で確かめられるところまでにし、本番で確かめる項目を PR に残す。本番の確認はマージの後にオーナーと行う。
- worker ごとに分ける資源：開発サーバー・Storybook・`wrangler dev` のポートと、ブラウザ操作のセッション名。並行して動くため。
- 実作業の上限（計画でオーナーが了承した値。SKILL.md の「依頼者の指定」に当たる）。修正の往復の上限は SKILL.md のまま変えない。上限に達したら止めて司令塔に知らせる。
- 製品の判断、文書どうしの食い違い、条件と実装が合わない点は、実装で埋めずに司令塔に聞いて待つ。聞くときは下の「オーナーへの質問」の型で書き、詳しい説明を Issue のコメントに書いてリンクを付ける。コメントの見出しは「相談（未決定）」にする（オーナーと同じ名義で投稿されるので、合意と取り違えないため）。司令塔はオーナーに戻す（下の「オーナーが不在の間」を除く）。
- 先にマージされた PR と競合したら、元のブランチを取り込んで解き、差分を再レビューしてから知らせる。
- 終わったときの報告：PR の URL、head、区分、観点ごとの判定とその対象の head、`pnpm check` と CI の結果、オーナーの確認が要る点、未確認事項。
- 先に終わった Issue からの申し送り（引き継いだ `SHOULD`、確かめていない点、Run の途中で決まったこと）。申し送りは Run の記録に書きためておき、後続の起動時に渡す。

使わないコマンドと扱わない操作は、依頼に加えて、起動の直後に worker の画面にも送る。送り先は 1 件ずつ明示し、送った後に worker の画面で届いたことを確かめる。

## 監視と応答

- 監視は自動で短い間隔（1 分程度）で回し、待機・質問・許可の確認・止まった worker・利用上限を知らせるようにする。
- worker が待機に入ったら、すぐにその画面と受信を読む。質問は届いているものをすべて処理してから、次の待機に戻る。
- 許可の確認：担当の worktree の中で終わる操作（ファイル編集、テストの実行、localhost を開くブラウザ）は 1 回ずつ許可する。「以後聞かない」は選ばない。パッケージを取得して実行するコマンド（`npx shadcn` による部品の追加を含む）は断り、`pnpm exec` や `pnpm agent:shadcn` に読み替えさせる。

## オーナーへの質問

オーナーは worker の作業の経緯や考えを知らない。質問だけを読んで判断できるように、次の型で書く。worker が司令塔に聞くときも同じ型にする。

1. **何を決めるか**：判断の対象だけを 1 文で。仕組みの説明は入れない。
2. **なぜ今聞くか**：worker が何をしようとして、どこで道が分かれたか（2〜3 文）。
3. **選択肢**：2〜4 個、推奨を先頭に。それぞれ、オーナーから見て変わること（画面、使い方、後で困ること）を先に書き、作りの違いは最後に一言だけ。
4. **worker の考え**：なぜその案を推すか。
5. **決めないと何が止まるか**、後から変えられるか。変えられるなら、変えるときの手間も一言書く（文を 1 か所直すだけ、保存済みの記録も直す、など）。
6. **詳しい説明**：worker が Issue に書いたコメントへのリンク。

- PR・マージ・CI のように、オーナーが普段使う開発の語はそのまま使う。実装の中の語（HTTP の状態コード、テーブルやキャッシュの方式、設定の名前など）は、一言で言い換え、元の語を括弧で添える（例：ファイルが変わっていないかを確かめる印（ETag））。元の語は消さない（オーナーが元の語を調べたり覚えたりできるように）。語の意味の言い換えは司令塔が書いてよい。オーナーから見て変わることと worker の考えは、worker の説明から書く。
- 同じ説明を複数の欄で繰り返さない。仕組みの細部は、選択肢の末尾か詳しい説明に回す。
- 計画の番号や前の会話に頼らない。質問だけで読めるようにする。
- worker の説明を短くしても、選択肢と、それぞれの理由は落とさない。
- worker の質問に足りない項目があれば、worker に聞き返してから聞く。司令塔が推測で埋めない。
- 1 回に聞くのは 4 件まで。関係するものをまとめて聞く。
- 型の全文はメッセージの本文に書く。選択肢を示して選んでもらう仕組みは、選ぶ操作にだけ使う（その仕組みの欄に型を押し込まない）。
- オーナーが答えたら、司令塔がその判断を Issue のコメントに「オーナー判断（日付）」として書き、worker に知らせる。オーナーが選んだ選択肢は質問の文のまま書く。条件が変わるなら、変わった条件もそのコメントに書く。

例（保存に失敗したときの表示）：

- 何を決めるか：保存に失敗したときに出す一言を、失敗の理由によって変えるか。
- なぜ今聞くか：worker が保存の失敗の表示を作っていて、今の一言「記録は変わっていません」が事実と違う場合があると気づいた。
- 選択肢：
  1. 分ける（推奨）：保存できなかったと確かなときだけ「記録は変わっていません」と出す。保存できたか分からないとき（通信が切れたなど）は、記録を読み直して最新の状態を見せる。作りは、失敗の種類ごとに表示を分ける。
  2. 今のまま：どの失敗でも「記録は変わっていません」。まれに、実は保存できていたのにこう出る。
- worker の考え：事実と違う表示を出さないため。
- 決めないと：この Issue の PR が止まる。後から変えられる（表示を分ける処理を戻すだけで、記録には影響しない）。
- 詳しい説明：Issue のコメント（リンク）

## マージ

マージは司令塔が行う。条件：

1. 区分に必要なすべての観点が pass で、その pass が**最終の head** のものである。PR のレビューの記録と worker の報告で、観点ごとの対象の head を確かめる。古い head の pass が混じっていたら、同じ worker に新しい head までの差分の再確認を頼む。
2. CI が成功している。
3. 競合がなくマージできる。
4. 計画で「オーナーの確認後」とした点が確認済み。
5. `main` 向けの PR は、オーナーが了承している（`main` へのマージは本番へのデプロイになる）。

- worker の PR は squash でマージする。`main` を統合ブランチに取り込む PR はマージコミットにする（squash すると取り込みの履歴が残らず、統合ブランチを `main` に入れるときに競合の元になる）。
- PR の文言や小さな振る舞いの確認で司令塔が判断したことは、報告に書く。
- マージした後、続きがなければ worker を解放する（「役割」）。worker が起動した背景のプロセス（テストの watch、開発サーバー）が残っていないかを確かめて終了させる。残ると負荷が上がり、ほかの worker のテストが時間切れで落ちる。
- 複数の PR が入って初めて確かめられる動き（API と画面をつないだ表示など）は、司令塔が確かめて Issue に結果を書く。

## 止める・再開する

- **オーナーが止めたとき**：worker に区切りで止めるよう伝え、止めた地点（ブランチ、head、レビューの途中経過、残り）を SKILL.md の実行記録に書かせる。司令塔は Run の記録に、作業中の Issue と worker の対応、まだ起動していない Issue を書く。再開のときは同じ worker に「再開」を伝える。worker が残っていなければ、同じ worktree で新しい worker を起動し、最初にブランチ・未 push のコミット・レビューの途中経過を伝える。
- **利用上限**：5 時間の利用上限が 90% を超えたら、新しい起動とマージを止め、worker を区切りで止める。上限のリセットを確かめてから再開する。
- **worker が上限に達したとき**：司令塔は上限を延ばさない。残りを後続の Issue への申し送りにするか、オーナーに戻す。
- **オーナーが不在の間**（寝ている間など。計画でオーナーが了承した任せ方に従う。既定は次のとおり）：
  1. PR の文言や小さな振る舞いの確認は、司令塔が判断してマージし、後で報告する。
  2. PRD・ドメインモデル・過去の決定を変える判断は推奨案で進め、PR と Issue に「要確認」と書く。統合ブランチ向けの PR はマージしてよい（`main` に入る前に戻せる）。
  3. 途中で見つけた小さな課題は起票してよい。
  4. 計画の止める地点で止める。範囲外の Issue と、統合ブランチを `main` に入れる PR は扱わない。

  計画で「オーナーの確認後」とした点は、不在の間もマージしない（1 より計画を優先する）。

## 報告

区切り（止める地点、オーナーの停止、不在の明け）ごとに、次を並べる。

- マージした PR と Issue
- 司令塔が判断した点
- 「要確認」の点（推奨案で進めた判断。「オーナーへの質問」の型で書き、「決めないと何が止まるか」の代わりに、進めた案と、戻すときの手間を書く）
- 起票した Issue
- 止まった点とその理由、残りの Issue

Run の間は、司令塔の判断・起票・停止を時刻つきで Run の記録に書きためて、報告の材料にする（マージした PR は GitHub から辿る）。

## Run の記録

Run の記録は、Git 管理外でセッションに依らない場所に置く（例：司令塔の worktree の `.tools/harness/runs/<Run の名前>/`）。セッションの一時領域には置かない（セッションが終わると読めなくなる）。進捗の正本は Issue・PR・CI で、Run の記録には、それらに書かない司令塔の材料（計画、Issue と worker の対応、申し送り、判断と停止のメモ）だけを置く。
