# 司令塔：複数の Issue を並列に進める

独立した Issue を同時に進めるとき、1 つのセッションが司令塔になり、Issue ごとに worker のセッションを動かす。一続きの並列実行を Run と呼ぶ。並列実行の道具（worktree の作成、worker の起動・監視・メッセージ）は問わない。道具の操作手順・スクリプト・既知の不具合はこの Skill に書かず、使う人の環境に置く。

## 役割

| 役割 | 担当 | やらないこと |
| --- | --- | --- |
| 司令塔 | 計画、起動、伝達、監視、マージ、統合の確認、報告 | 実装とレビュー（worker の worktree を編集しない） |
| worker | 1 つの Issue を SKILL.md の「Issue を実装する」の手順で、レビューと PR 作成まで | マージ、ほかの Issue の作業 |
| オーナー | 計画の了承、製品の判断、Run の停止と再開 | — |

- 1 Issue＝1 worker＝1 worktree。小さな Issue を 1 つの PR にまとめるときは計画に書く。
- worker の Reviewer は worker 自身が起動する。司令塔は Reviewer を起動しない。
- マージした PR の続き（範囲内の小さな直し）は、同じ worker に新しい依頼として渡す。

## Run の計画

起動の前に計画を作り、オーナーの了承を得る。了承の前に worker を起動しない。計画に書くこと：

1. 対象の Issue と、それぞれの向き先のブランチ（`main` か統合ブランチか）。
2. 依存：どの PR がマージされたら、どの Issue を起動できるか。
3. 同時に動かす worker の数（既定は 3）と組み合わせ。触るファイルが重ならない組にする（API と画面のように別の領域どうし）。同じファイルを触る Issue は順に並べる。
4. Issue ごとのモデルと effort。既定は、ドメインや土台が Opus、画面が中心のものが Sonnet、effort は high。
5. オーナーに確認してからマージ・着手するもの（語の最終確認、規則の決定、画像での比較など）と、範囲外にするもの。
6. 止める地点（どこまで進めたら止めるか）。

既定の値はオーナーが Run ごとに変えられる。依存の前提が `main` 向けの PR なら、それを `main` にマージし、`main` を統合ブランチに取り込んでから後続を起動する（道具の依存の機能では、この順を表せないことがある）。取り込みは司令塔が PR で行い、CI の成功を確かめてからマージする。

## worker への依頼

依頼に書くこと：

- 担当の Issue、worktree の元のブランチ、PR の向き先。統合ブランチ向けの PR は `Closes` が効かないので `Refs` にする。
- 守る手順：AGENTS.md と SKILL.md の「Issue を実装する」に従い、レビューまで行う。マージはしない。担当外の Issue は編集しない。
- 使わないコマンド：パッケージを取得して実行するもの（`npx`・`npm`・`pnpm dlx`）は使わず、`pnpm exec`・`pnpm test`・`pnpm check` に読み替える。許可の確認で止まるため。
- 扱わない操作：秘密の値、デプロイ、本番の資源への操作。本番でしか確かめられないこと（デプロイ後の確認など）は、ローカルと CI で確かめられるところまでにし、本番で確かめる項目を PR に残す。本番の確認はマージの後にオーナーと行う。
- worker ごとに分ける資源：開発サーバー・Storybook・`wrangler dev` のポートと、ブラウザ操作のセッション名。並行して動くため。
- 実作業の上限（Issue の大きさに合わせて司令塔が決める。SKILL.md の「依頼者の指定」に当たる）。
- 製品の判断、文書どうしの食い違い、条件と実装が合わない点は、実装で埋めずに司令塔に聞いて待つ。司令塔はオーナーに戻す（下の「オーナーが不在の間」を除く）。
- 先にマージされた PR と競合したら、元のブランチを取り込んで解き、差分を再レビューしてから知らせる。
- 終わったときの報告：PR の URL、head、区分、観点ごとの判定、`pnpm check` と CI の結果、オーナーの確認が要る点、未確認事項。
- 先に終わった Issue からの申し送り（引き継いだ `SHOULD`、確かめていない点、Run の途中で決まったこと）。申し送りは Run の記録に書きためておき、後続の起動時に渡す。

使わないコマンドと扱わない操作は、依頼に加えて、起動の直後に worker の画面にも送る。送り先は 1 件ずつ明示し、送った後に worker の画面で届いたことを確かめる。

## 監視と応答

- 監視は定期的に行い（30 分を目安）、止まった worker、許可の確認、利用上限を拾う。
- worker が待機に入ったら、すぐにその画面と受信を読む。質問は届いているものをすべて処理してから、次の待機に戻る。
- 許可の確認：担当の worktree の中で終わる操作（ファイル編集、テストの実行、localhost を開くブラウザ）は 1 回ずつ許可する。「以後聞かない」は選ばない。パッケージを取得して実行するコマンドと、部品の追加は断り、`pnpm` の中のコマンドに読み替えさせる。

## マージ

マージは司令塔が行う。条件：

1. 区分に必要なすべての観点が pass で、その pass が**最終の head** のものである。PR のレビューの記録で、観点ごとの対象の head を確かめる。古い head の pass が混じっていたら、同じ worker に新しい head までの差分の再確認を頼む。
2. CI が成功している。
3. 競合がなくマージできる。
4. 計画で「オーナーの確認後」とした点が確認済み。

- squash でマージする。PR の文言や小さな振る舞いの確認で司令塔が判断したことは、報告に書く。
- マージした後、worker を解放し、worker が起動した背景のプロセス（テストの watch、開発サーバー）が残っていないかを確かめて終了させる。残ると負荷が上がり、ほかの worker のテストが時間切れで落ちる。
- 複数の PR が入って初めて確かめられる動き（API と画面をつないだ表示など）は、司令塔が確かめて Issue に結果を書く。

## 止める・再開する

- **オーナーが止めたとき**：worker に区切りで止めるよう伝え、止めた地点（ブランチ、head、レビューの途中経過、残り）を SKILL.md の実行記録に書かせる。司令塔は Run の記録に、作業中・待ち・済みの Issue を書く。再開のときは同じ worker に「再開」を伝える。worker が残っていなければ、同じ worktree で新しい worker を起動し、最初にブランチ・未 push のコミット・レビューの途中経過を伝える。
- **利用上限**：5 時間の利用上限が 90% を超えたら、新しい起動とマージを止め、worker を区切りで止める。上限のリセットを確かめてから再開する。
- **オーナーが不在の間**（寝ている間など。オーナーが Run ごとに決める。既定は次のとおり）：
  1. PR の文言や小さな振る舞いの確認は、司令塔が判断してマージし、後で報告する。
  2. PRD・ドメインモデル・過去の決定を変える判断は推奨案で進め、PR と Issue に「要確認」と書く。
  3. 途中で見つけた小さな課題は起票してよい。
  4. 計画の止める地点で止める。範囲外の Issue と、統合ブランチを `main` に入れる PR は扱わない。

  計画で「オーナーの確認後」とした点は、不在の間もマージしない（1 より計画を優先する）。

## 報告

区切り（止める地点、オーナーの停止、不在の明け）ごとに、次を並べる。

- マージした PR と Issue
- 司令塔が判断した点
- 「要確認」の点
- 起票した Issue
- 止まった点とその理由、残りの Issue

Run の間は、マージ・判断・起票・停止を時刻つきで Run の記録に書きためて、報告の材料にする。

## Run の記録

Run の記録（計画、Issue と worker の対応、申し送り、経過）は、Git 管理外でセッションに依らない場所に置く（例：司令塔の worktree の `.tools/orch/<Run の名前>/`）。セッションの一時領域には置かない（セッションが終わると読めなくなる）。進捗の正本は Issue・PR・CI で、Run の記録には、それらに書けない司令塔の材料だけを置く。
