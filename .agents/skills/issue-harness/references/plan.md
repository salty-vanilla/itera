# 要件整理・必要時の設計

## 要望を Issue にする

既存 Issue、PRD とドメインモデルの該当箇所、関連する実装を対象領域だけ調べる。`.github/ISSUE_TEMPLATE/` を使い、重複 Issue を作らない。

- 目的：誰の何を解決し、何が変わるか。PRD のどのコア体験（Backlog / Planning / Today / Retro）または MVP 完了条件に対応するか。
- 範囲：今回含むもの・含まないもの。PRD §11「対象外」に触れないか。
- 受け入れ条件：正常時の成果と、関係する境界・失敗時の条件を少数。観察・検証できる形にする。ドメインの不変条件に関わるなら番号で挙げる。
- 根拠：PRD / ドメインモデルの節、または合意を記録した Issue。基盤・調査などは依頼そのものを根拠にする。
- 未決事項：実装を止める製品判断と、実装担当に任せる細部を分ける。PRD §14 とドメインモデル末尾の未決事項に当たる場合は明記する。

要件・範囲を変える質問を優先し、資料で解決できることや通常の実装判断でユーザーを止めない。合意したら Issue に日付と判断を書き、製品要件の変更なら PRD / ドメインモデルの更新も同じ PR で提案する（どの文書を更新するかを先に決める。PRD §15）。

目的・範囲・確認方法・根拠が揃い、重要な未決がなくなったら整理を終える。1 Issue は独立して受け入れられる変更を基本にし、工程ごとに Issue を増やさない。

## 設計相談だけを受けた場合

依頼された論点、守る条件、候補、推奨と理由、検証方法を返す。ドメインモデルや API 契約の変更が必要なら影響範囲を明示する。重要な判断がなければ局所設計は実装担当に任せる。

設計役はコードを書き換えず、Issue や PR に直接投稿しない。親に草案を返す。

返す内容：実装可能か / 不足する判断、Issue 草案または既存 Issue への変更案、必要な設計判断、参照先。
