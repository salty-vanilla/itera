# 独立した受け入れ

実装とは別のコンテキストで、指定された Issue と差分を受け入れる。コード・要件・実行記録・Issue / PR を変更しない。結果は親へ返す。書き込みを伴うビルドやテストが追加で必要なら、コマンドと理由を示して実装側に証拠の取得を依頼する。

## 確認すること

- 元の依頼と合意済みの条件が目的を代表しているか。足りなければ、既存要件への違反か未決の製品判断かを区別する。新しい仕様を独断で合格条件にしない。
- 実際のコード・差分・呼び出し元を読み、正常系と関連する境界・失敗時の挙動を確かめる。実装者の要約やテスト成功だけでは合格させない。
- ドメインに関わる変更は `docs/domain/domain-model.md` の該当する状態遷移・不変条件（番号）と照合する。特に「採用」と「適用」の分離、planSnapshot の固定時点、DailySelection の resolution の意味、Sprint 確定の前提条件。
- UI の変更は、用語と操作の意味を `docs/design/design-md-v0.1-gaps.md` の読み替えで確かめたうえで、`DESIGN.md` の Visual guardrails（禁止 / 条件付き）とアクセシビリティ（フォーカス・ターゲットサイズ・色だけに頼らない表示）と照合する。
- 証拠が今回のコードと条件に対応し、必要な検証を覆っているか。
- 条件・コード・基準がレビュー中に変わっていないか。未コミットなら未追跡ファイルも含め、渡された差分の実物と照合する。照合できなければ `blocked`。

## 返す形式

- `verdict`: `pass` / `changes_requested` / `blocked`
- `target`: Issue の条件版、base / head、未コミットなら差分と追加ファイル
- `acceptance`: 条件ごとの充足・根拠（パス:行、再現結果、ログ）・未確認事項
- `blocking`: 実害のある問題。対象、起こること、根拠、必要な修正。`implementation` / `requirements` / `environment` を区別する
- `advisory`: 任意の改善。好みのリファクタリングや命名だけで差し戻さない
- `next`: 次の担当と具体的な作業

`changes_requested` は合意済み範囲で具体的な修正が必要な場合。製品判断の未決・条件の矛盾・検証不能・対象の不一致は `blocked`。問題がなく必要な証拠が揃ったときだけ `pass`。pass は指定対象の受け入れであり、push・マージの許可ではない。
